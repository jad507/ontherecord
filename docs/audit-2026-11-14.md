# Architecture audit and roadmap (November 14, 2026)

An audit of On the Record at commit `12e3419`, asking one question: what stops a social scientist with a
different study (interviews, classrooms, focus groups, video, another language, their own codebook) from using
this, and what should change so they can. Written for whoever builds next, person or agent. Each item says what
is wrong, where, why it matters, what to build, and how to know it is done.

Baseline when this was written: 96 tests pass, 1 skipped. The workspace on shiro holds 29 runs, 217 receipts and
3 review sets.

## How to use this document

- Read "The diagnosis" and "Rules that must not be broken" before touching anything. The rules are the part an
  implementer is most likely to get wrong, because breaking them looks like tidying up.
- Items are numbered (A1, B3...) and ordered by dependency inside each part. "Order of work" at the end gives one
  sequence across all parts.
- Sizes: S is under half a day, M is one or two days, L is most of a week.
- Each item has a "Done when" line. Do not call an item done on anything less.
- Where an item says "decide with Jeff", stop and ask. Those are choices about his research, not about code.

## The diagnosis

**The engine generalized. The data did not.**

The engine is the recipe, the runner, the content-addressed store, receipts, checks, the `same_source` trace and
the one-at-a-time queue (`recipe.py`, `runner.py`, `worker.py`, `store.py`, `hashing.py`, `jobs.py`). None of it
knows what a council meeting is. It is small, tested and sound. Keep it as it is.

Everything above the engine was ported from two specific projects and still has their shape:

1. **Every stage invents its own file format, and every reader finds data by stage name.** `transcript.json`,
   `aligned.json`, `blocks.json`, `words.json` and `comments.json` are five different shapes for "stretches of a
   recording, with text, maybe a speaker, maybe a label". The Library, Compare, Reviews, the assistant's tools
   and the page's previews each name the stages they know and reach into those shapes:
   - `library.py:64-76` (`_view`) lists six stage names by hand and special-cases `nemotron_transcribe`.
   - `library.py:210-221` (`HEADLINE`) is a table keyed by stage name.
   - `reviews.py` `from_run` has four kinds, each tied to named stages and their JSON fields.
   - `static/app.js:510-513` previews an output by checking `name === "blocks"`, `name === "comments"`.
   - `tools.py:188` is a `public_comments` tool.
   - Count of stage-name string literals outside `stages/`: 32 in `library.py`, 11 in `reviews.py`, 21 lines in
     `app.js`.

   So adding one new kind of work means editing about eight files. The Nemotron stage shows the cost: to fit in,
   it had to imitate pyannote's and Whisper's exact files (two RTTMs and a stats file it has no real use for).

2. **Coding, the central act of qualitative research, is not a concept in the program.** There is no codebook.
   The machine codes through `extract_comments`, whose question, schema and prompt are fixed to public comment
   in Lancaster. People code on the Check page, where codes are ten key names stored inside one review set
   (`reviews.py:47`, placeholder names for a council meeting). The two write different shapes and never meet, so
   the program can answer "does the machine agree with my coders?" for exactly one hard-wired question.

3. **The unit of work is a recording, and everything smaller is buried.** Segments, turns, blocks and clips live
   inside JSON files with no shared ids. `stress_set` packs a whole dataset into one zip to pass as one item, so
   one bad clip of 218 reruns all 218 and no clip has its own receipt.

4. **The screens are arranged by mechanism, not by a researcher's day.** Build, Jobs, Results and Setup are
   engine words. The only path that needs no recipe is "Transcribe a recording". Coding by hand with your own
   codes needs a command line (`review new RUN --kind check --codes "..."`).

The fix for 1 to 3 is one idea: **a few shared data formats that stages declare, and readers that look for a
format, not a stage.** Parts A and B build that. Part C is the screens. Part D is smaller faults found on the
way.

## Rules that must not be broken

These follow from how the cache works. Read `hashing.py` and `recipe.py:resolve_settings` to see why.

1. **Never change what an existing stage writes.** A stage's output bytes are hashed into receipts, and into the
   keys of everything downstream. The ISLS 2027 paper's numbers and the Research-a-thon notes cite those hashes.
   `download`, `audio`, `diarize`, `transcribe`, `align`, `blocks`, `extract_comments`, `stress_set`,
   `whistress`, `stress_read`, `word_choices` and `nemotron_transcribe` are frozen. New formats come from **new
   stages** and from **readers that adapt the old files in memory** (A1). Do not "migrate" the store.

2. **Never change an existing setting's default.** A default is filled in and hashed into the key
   (`recipe.py:160`, `v = given.get(k, s.default)`). Change `transcribe.language` from `"en"` to detect, and
   every recipe that left it out gets new keys: the whole corpus runs again and old receipts stop matching. To
   give new users different behavior, write the value into the recipe from `presets.py`, which is what it is
   for.

3. **Adding a setting to an existing stage also changes every key of that stage**, because the new setting's
   default joins the hashed settings. Add settings only to new stages, or bump the stage's version knowingly and
   say so in the commit.

4. **Removing a `choices` list is safe.** Choices are checked but not hashed.

5. **Nothing a stage reads may come from outside its settings and inputs.** Not a project file, not item
   metadata, not speaker names, not the clock. If a stage needs it, it arrives as an input artifact with a hash
   (see A4 and C4 for the two places this bites).

6. **Keep what STATUS.md already decided:** one thing at a time, nothing goes online unless asked, every
   download pinned by SHA-256, the server answers only this machine, reviews are blind by construction, the
   answers log is append-only.

7. **Do not rewrite for tidiness.** `server.py` is one 770-line function and `app.js` one 1,375-line file. Both
   work. Split a piece only when an item here has you changing that piece anyway. No frontend framework, no
   build step: the installers and the "nothing is fetched" rule depend on plain files.

## Part A. Shared data formats (the spine)

### A1. Artifact types and readers (M) — do this first

**What.** Three formats cover nearly everything:

- **segments**: stretches of one recording.
  `{"format": "segments/1", "unit": "segment" | "turn" | "block" | "clip" | "interval",
    "units": [{"id": "t0007", "start": 12.3, "end": 19.8, "text": "...", "speaker": "SPEAKER_02",
               "words": [{"start", "end", "word", "p"}]}]}`
  `text`, `speaker` and `words` are optional. A unit with no text is legal: that is what a stretch of video is
  (Part E).
- **annotations**: labels on units or on spans of time.
  `{"format": "annotations/1", "codebook": {"name", "sha256"}, "by": {"kind": "model" | "person", "id": "..."},
    "annotations": [{"id", "target": {"units": ["t0007", "t0008"]} | {"start": 12.3, "end": 19.8}
                                    | {"unit": "t0007", "word_from": 3, "word_to": 9},
                     "code": "public_comment", "attributes": {"position": "oppose", "summary": "..."},
                     "note": ""}]}`
  Three target kinds on purpose: whole units (what a model returns), a time span (video, overlapping speech),
  and a word span inside a unit (what the Check page records).
- **speakers**: who spoke when. RTTM, as now.

Add to `Stage` a class attribute `types: dict[str, str]`, mapping each artifact it makes to a format
(`{"transcript": "segments", "aligned": "segments", "blocks": "segments", "words": "segments",
"comments": "annotations"}`). Declaring a type changes no output and no key.

Add `src/ontherecord/artifacts.py` with `read_segments(path) -> dict` and `read_annotations(path) -> dict`. A
file that carries `"format"` is returned as is. Otherwise the reader adapts the old shapes in memory:

| Old file | Becomes |
|---|---|
| `transcript.json` `segments[]` | units, id `s{index}`, unit `segment` |
| `aligned.json` `segments[]` | the same, with `speaker` |
| `blocks.json` `blocks[]` | units, id `b{block_id}`, unit `block`; `category` kept as an extra field |
| `words.json` `segments[]` | units with `words` |
| `comments.json` `comments[]` | annotations, target `{"units": ["b12", "b13"]}`, code `public_comment`, the six named fields as `attributes` |

**Why this way.** Rule 1 forbids rewriting the old files, and the old stages must keep producing them. Adapting
on read gives every reader one shape while the store stays byte-identical. Ids derived from position are stable
because a store entry never changes.

**Trap.** Do not bump any stage version for this. Do not add a `format` field to an old stage's output.

**Done when:** `artifacts.py` reads every existing output in shiro's store without error (a test walks a fixture
of each of the five shapes); `ontherecord stages --json` shows types; no file under `store/` changed (check with
`git`-style before/after hashes of two store entries).

### A2. Readers look for a type, not a stage (M)

**What.** Replace the stage-name lookups with one helper: "for this run and item, the latest step that makes an
artifact of type T" (walking `rec["stages"]` and the registry's `makes` and `types`, as `Library._steps`
already half does).

- `Library._view`: transcript = latest `segments` artifact that has text, preferring one with speakers; audio =
  the `audio` that step's inputs trace to (keep this: the player must play what the transcriber heard);
  annotations = every `annotations` artifact, listed by step name. Delete the `nemotron_transcribe` special
  case.
- `HEADLINE`: move to the stages. Add `headline: tuple[str, str] | None` to `Stage` (a metric path and its
  wording, for example `("words", "words")`), read by `compare`.
- `app.js:510-513`: preview by type. One table for any `segments`, one for any `annotations` (columns from the
  attributes present), raw JSON for the rest.
- `reviews.from_run`: `transcript` and `speakers` kinds take any `segments`; `check` takes any `segments` with
  `words`.
- A stage from a plugin that is not installed has no known types. Fall back to raw JSON, as `_steps` does now.

**Why.** After this, a new transcriber, a new unit builder or a new coder shows up in the Library, Compare and
Review with no edits outside its own file. That is the test of whether the architecture generalized.

**Done when:** `tests/stages_for_tests.py` gains a toy stage making a `segments` artifact and a toy stage making
`annotations`; a run of them shows a transcript and a codes tab in `Library.recording()` with no production
code naming them. `grep -c` for stage-name literals in `library.py` drops from 32 to under 5.

### A3. A `turns` stage (S)

**What.** A new stage: `needs = ("aligned",)`, makes `turns` of type `segments`, written in the new format
directly. Settings: `max_gap_s` (default 5), `max_turn_s` (default 60; a longer turn is cut at a segment
boundary and numbered as parts). It merges consecutive segments of one speaker.

**Why.** There are three private copies of this logic: `blocks.merge_segments`, `reviews.turns`, and the Check
set builder. `blocks` also bakes in a council heuristic (`recurring` against `commenter_candidate`,
`blocks.py:45-51`) that means nothing in an interview. A neutral turn is the unit most coding works on.

**Trap.** Leave `blocks` and `reviews.turns` alone (rule 1; existing sets were cut by `reviews.turns`). New work
uses the stage.

**Done when:** on a fixture, `turns` with `max_gap_s: 5, max_turn_s: 60` gives the same boundaries as
`reviews.turns` does today.

## Part B. Coding as a first-class thing

### B1. Codebooks (S)

**What.** A codebook is a YAML file, hashed like a prompt (`Setting(kind="file")`), so its full text lands in
every receipt:

```yaml
name: public-comment
question: Is this speech by a member of the public addressing the body?
multiple: false            # may one unit carry several codes?
codes:
  - id: public_comment
    name: Public comment
    definition: A resident or stakeholder addressing the body with an opinion, concern, request or question.
    include: ["speaking at a public hearing", "reading a statement for a neighbor"]
    exclude: ["council members", "invited presenters", "the clerk calling names"]
attributes:                # optional free fields the coder also fills in
  - {id: position, choices: [support, oppose, mixed, neutral_or_question, unclear]}
  - {id: summary, help: one or two sentences in plain words}
```

Put shipped examples in `src/ontherecord/codebooks/` (found the way `resolve_file` finds prompts) and a
project's own in its project folder (C5). Validate on load: unique ids, non-empty definitions.

**Why.** The codebook is the one object a human coder, a model coder and the write-up all share. Today its
content is spread over a prompt file, a Python schema and a list of key names.

### B2. The `code` stage (L) — the highest-value item here

**What.** A new stage that applies any codebook to any `segments` artifact and writes `annotations`.

- `needs = ("units",)`. In a recipe: `- code: {codebook: my.yaml}` with `from: {units: turns}`. The runner wires
  by artifact name, so the generic input needs one small extension to `parse_stages`: when `from:` names a step,
  accept any artifact of that step whose **type** matches the type the stage asks for. Keep the name-based rule
  for everything else.
- Settings: `codebook` (file), `lens` (file, optional: a theoretical stance put before the codebook),
  `context` (`unit`: each unit alone; `window`: each unit with `window_size` neighbors either side as grey
  context; `whole`: the whole recording at once, answering by unit id), `mode` (`classify`: every unit gets an
  answer; `find`: list the stretches that match, as `extract_comments` does), and the model settings
  `open_model` already takes (`endpoint`, `model`, `context_tokens`, `offload`, `thinking`, `temperature`,
  `seed`, `max_tokens`).
- The model answers **by unit id only**, never by quoting. Keep this from `extract_comments`: the coded text is
  then the transcript's own bytes and can be checked. Build the JSON schema from the codebook (code ids as an
  enum; attributes as declared).
- Checks: `parsed` (fail), `unknown_ids` (warn), `unknown_codes` (fail), `coverage` in classify mode (warn when
  units got no answer), `windows` (how many pieces; warn when a `whole` recording did not fit and was cut).
- Outputs: `annotations` (the new format, with the raw responses kept beside the parsed ones, as now) and
  `annotations_csv`.
- Reuse `llm.py`, `usage.llm_metrics` and the windowing in `extract_comments.py` (import the functions; do not
  move them).

**Why `context` and `lens` are settings.** They are Jeff's two research claims made runnable. The ISLS paper is
about what batching changes: `context: unit` against `whole` is that experiment in one line. His "LLM coders can
forget" idea (the same coder under several theoretical lenses, like rotating graduate coders) is `lens`. With
receipts, two runs that differ in only one of these are provably that and nothing else.

**Trap.** `extract_comments` stays, frozen, as the paper's stage. Ship `codebooks/public-comment.yaml` and a
recipe that runs `code` on the eleven meetings beside it. The two will not match byte for byte and must not be
expected to; report how the comment counts compare.

**Done when:** a recipe with `turns` then `code` under a toy codebook passes against the test stub server; the
public-comment recipe runs on one real meeting through the queue and its annotations show in the Library's
codes tab (A2); `ontherecord plan` shows it cached on a second submit.

### B3. People and models write the same annotations (M)

**What.**

1. **Fix annotator identity first (a real fault, see D1).** Today every answer is recorded `by: "me"` and the
   latest answer per item wins regardless of who gave it.
2. A review set made for coding carries the codebook (its name and sha256, and the codes themselves so the set
   stays self-contained and unchangeable). `review new RUN --kind code --codebook my.yaml` replaces `--codes`.
   Keys 1-5 and Q-T go to the first ten codes; the rest are reached by a type-to-filter list. Show each code's
   definition on hover or on `?`: a coder who cannot see the definition is not applying the codebook.
3. `ontherecord review export SET --annotations` writes one `annotations` file per annotator, in the A1 format.

### B4. Agreement between any two coders (M)

**What.** `ontherecord agree A B [C...]`, where each argument is an annotations source: a run's step
(`RUN:step`) or a review set's annotator (`SET:name`). Output per code: how many each side applied, agreement,
Cohen's kappa for two coders, Krippendorff's alpha for more or for missing data, and with one side named as the
reference, precision, recall and F1. Plus the units they disagree on, as a list that opens in the player.

Unitizing: a model codes whole units, a person on the Check page codes word spans. Compare at the unit level (a
unit carries a code if any span in it does) and say so in the output. Do not invent a span-level statistic.

**Why.** This single command answers the questions a methods section needs: person against person (is the
codebook usable?), person against model (can the model be trusted?), model against model across lenses, context
sizes or model files (what does the setting change?). It is also the natural result screen for B2.

**Trap.** Look the formulas up (Krippendorff 2011, "Computing Krippendorff's Alpha-Reliability") and test
against a worked example from the source. Do not write alpha from memory.

**Done when:** tests reproduce a published worked example for kappa and for alpha; `agree` on the gold sample
set against `extract_comments` reproduces the agreement `review score` already reports for it.

### B5. Variants in a recipe (S, after B2)

**What.** Sugar over `as:`.

```yaml
- code: {codebook: frames.yaml}
  variants: {lens: [none, conflict.txt, care.txt], context: [unit, whole]}
```

expands at parse time into six ordinary steps named `code-lens-conflict-context-unit` and so on. Nothing in the
runner changes. `stress-benchmarks.yaml` shows the need: five hand-written `stress_read` entries.

## Part C. Usable without a command line

### C1. Arrange the screens by the work (M)

**What.** Order and name the tabs as a study goes: **Recordings** (the Library, with Import and Transcribe
inside it) → **Check** (transcripts by ear) → **Code** (by hand, or by model) → **Compare** (agreement, and
two runs side by side) → **Export**. Put Build, Jobs and Results under one **Runs** tab for people who want the
engine, and Setup under a gear. Ask stays.

Every action starts from a recording or a selection of them: tick recordings in the list, then "Transcribe",
"Check by ear", "Code by hand", "Code with a model", "Export". Each button writes a recipe or a review set
behind the scenes and shows it ("what will run", with the time estimate that already exists).

**Why.** A researcher thinks "these twelve interviews", not "a recipe whose source lists twelve files". The
recipe stays the record; it stops being the entry point.

**Trap.** Reorder and relabel; do not rebuild. The existing panels move, they are not rewritten.

### C2. A codebook editor (M, with B1)

A form: add a code, name it, define it, give examples to include and exclude; add attributes. It writes the
YAML of B1 into the project folder. Without this, B2 is a feature for programmers only. Offer "start from a
copy" of a shipped codebook.

### C3. Plain errors (S)

`worker.py:113-116` stores a Python traceback as the cell's error and the page shows it. Add
`class UserError(Exception)` in `stages/base.py` with a message and a `fix`. Raise it for the failures a person
can act on: no Hugging Face token, the model's terms not accepted, model file not downloaded, ffmpeg missing,
out of GPU memory, a file with no audio stream. The cell shows the message and the fix; the traceback goes to
the log only. Unknown exceptions keep today's behavior with a first line that says "this is a fault in the
program; the log has the details".

### C4. Speaker names (M) — decided Oct 25, not built

Build as `docs/projects-and-folders.md` says: names in `project.yaml`, edited from the player.

**Rule 5 applies.** Names are laid over the transcript when it is shown or exported. They are never written into
store files, and by default they are **not** given to the `code` stage: a model that reads "Chair Smith" codes
differently from one that reads "SPEAKER_02", and the receipt would not show why. If Jeff wants named speakers
in the model's input, the names must become an input artifact (a tiny `names` stage that hashes the mapping).
**Decided with Jeff, Nov 14:** the model gets `SPEAKER_02`, not names, by default. Named input, if ever wanted, only
through the hashed `names` artifact above.

### C5. Projects (L) — decided Oct 25, not built

Build as decided: labels in one workspace, a project picker, `Projects/<name>/Transcripts/` written when a run
ends, never overwriting a file a person edited. Add to the decided design: `Projects/<name>/codebooks/`, and
`project.yaml` holding the annotators' names (B3). Until projects exist, every study's recordings, sets and
codebooks sit in one heap, which is the first thing a second study runs into.

### C6. Getting work in and out (M for the first three, L for the rest)

Researchers do their analysis in NVivo, ATLAS.ti, MAXQDA, ELAN, Praat, R or Excel. If work cannot move both
ways, the program is a detour.

**Out.** Today `.txt`, `.srt` and `.vtt` are built in the browser (`app.js:639`), so the command line, agents
and the `Transcripts/` folder cannot make them. Move them to a new `exports.py`, and add:

1. `.txt`, `.srt`, `.vtt` (moved), with speaker names applied. (S)
2. `.csv`, one row per unit: recording, its metadata columns (D4), unit id, start, end, speaker, text, and one
   column per code and attribute, per coder. This is what R and Excel users need and it is cheap. (S)
3. `.docx`, one paragraph per turn with the speaker and a time stamp. All three QDA programs import this. (S)
4. ELAN `.eaf` (a tier per speaker, a tier per codebook) and Praat `.TextGrid`. (M)
5. REFI-QDA `.qdpx` (codebook and coded segments, exchanged by NVivo, ATLAS.ti and MAXQDA). (L) Read the
   standard at qdasoftware.org before writing a line; do not write the XML from memory.

Every export ends with, or sits beside, its provenance: run id, the receipt keys of the transcript and the
annotations, the codebook's sha256. That line is the product.

**In.** A stage `import_transcript` making `segments` from an existing transcript: `.vtt` and `.srt` (Zoom and
Teams write these, with "Name: text" lines that give speakers), and plain text with "Speaker: text" paragraphs.
Many labs already have transcripts and only want checking, coding and agreement. With this they can start at
Check or Code with no Whisper and no GPU. (M)

### C7. README (S)

Jeff found it opaque (Oct 25). Open with what it does in three lines and three pictures (transcribe; check and
code; compare coders), then install. Move the phase-inversion story to a "Why receipts" section lower down. Say
plainly where it runs today (Linux tested; Windows and macOS untested).

### C8. Windows and macOS (L) — the largest adoption risk

Most social scientists use a Mac or a Windows laptop with no NVIDIA card. Neither system has been tried
(STATUS.md, week 4). Do the Windows walkthrough first, since Jeff has the machine.

On a Mac, Whisper runs on the processor (`bootstrap.fit`: `large-v3-turbo`, `int8`), because CTranslate2 has no
Apple GPU backend. **Measure before building anything:** minutes of compute per hour of audio on a real Mac. If
it is worse than about 30, add a second transcriber as a new stage (whisper.cpp has Metal support) that makes
the same `segments` type. After A1 and A2 that is one file. Check current backend support in the projects'
own documentation at the time; do not rely on this note.

## Part D. Faults and risks found on the way

### D1. Two annotators overwrite each other (S) — fix before anyone else codes

`reviews.latest` (`reviews.py:140`) and `scoring_answers` (`reviews.py:286`) key answers by item only.
The server accepts a `by` field (`server.py:89`) but neither page ever sends one, so every answer is `"me"`.
If a second person opens the same set, their answer replaces the first person's in progress, scores and export,
and the set looks finished to them from the start.

**Build:** an annotator name, asked once per browser and shown in the header; sent with every answer and
reveal. Key `latest`, `scoring_answers`, `progress` and `export_rows` by `(item, by)`. `machine_seen` is per
annotator. Progress is per annotator. Old rows with `by: "me"` stay valid as an annotator called "me".

**Done when:** a test has two annotators answer the same item differently and both answers survive in export
and in scoring.

### D2. Local files are hashed in full on every plan (S)

`recipe.source_identity` runs `sha256_file` on every local source, once per `Runner`, and a `Runner` is built
for every plan, estimate and submit. Fifty two-gigabyte interview videos is 100 GB read before anything starts,
each time the Build tab refreshes. This will be the first thing an interview researcher feels.

**Build:** a cache in the workspace (`hashcache.db`, SQLite): resolved path, size, mtime in nanoseconds →
sha256. Use it in `source_identity`. A changed size or mtime rehashes. `ontherecord plan --rehash` ignores the
cache. Say in AGENTS.md that a file altered with its size and mtime preserved will not be noticed.

### D3. A setting can say one thing and the receipt's key another (S)

`transcribe.py:55-64`: on a card without fast float16, `compute_type: float16` silently becomes `int8_float16`.
It is logged and put in the metrics, but the key still says float16. `device` is `in_key=False` everywhere,
though a transcript made on the processor is not byte-identical to one made on a GPU.

On one machine this is harmless. It becomes a wrong answer the day a store is shared between machines, which is
the plan for Slurm on ROAR: the laptop will reuse the cluster's result under the laptop's settings, or the
reverse.

**Build (no key changes; rule 2):** when a cached receipt's host, device or `compute_type_used` differs from
this machine's, `plan` and the grid say so ("reused; made on roar-gpu12, cuda, float16"). Add a `fallback`
check with status `warn` in `transcribe` and `word_choices` when the compute type used is not the one asked for
(a new check is not an output byte and changes no key). Write in AGENTS.md: one store per kind of machine, until
a later decision puts the device in the key.

### D4. Recordings have no metadata (M)

`Item` is `id, url, path, title`. A study's recordings have a participant, a site, a condition, a date, a wave.
Today the date is guessed by matching an English month name in the title (`library.py:196`,
`extract_comments.py:60`), and nothing else exists. Exports without these columns need hand-merging in Excel.

**Build:** a recipe source `manifest: recordings.csv`, with columns `id`, `path` or `url`, optional `title` and
`date`, and any others. The others become the item's metadata, shown in the Library and written to exports.

**Rule 5 applies.** Metadata is not part of any key (relabelling a participant must not rerun Whisper), so no
stage may read it. It lives in the run record. A stage that truly needs a per-recording value (true labels for
scoring) gets it as an input artifact from a small `metadata` stage that hashes that recording's row.

This also gives item ids a proper answer. Today a local file's id is its file name (`recipe.item_for_file`), so
`P01/audio.m4a` and `P02/audio.m4a` collide (the recipe is refused, correctly, but the only remedy is to name
each file by hand) and renaming a file makes it a new recording that is processed again. With a manifest the id
is the researcher's own. Without one, when names collide, prefix parent folder names until they are unique.

**Rejected:** ids from content hashes (unreadable, and they would orphan the present store), and dropping the
item id from the key (same orphaning).

### D5. Sending recordings off the machine is silent (S)

Any stage with an `endpoint` setting accepts any URL (`extract_comments`, `stress_read`, and B2's `code`). A
recipe copied from a colleague can send a transcript to a remote server with nothing on screen but a URL in a
settings list. For data under an ethics protocol, that is the worst thing this program can do.

**Build:** in `llm.open_model`, when the endpoint's host is not this machine, refuse unless `machine.yaml` has
`allow_remote_endpoints: [host, ...]` naming it. When allowed, add a `leaves_machine` check with status `warn`
naming the host, so the plan, the grid and the receipt all show it. Off by default.

### D6. Nothing enforces "bump the version when the code changes" (S)

`Stage.version` is raised by hand. Forget once, and old outputs are reused for new code with nothing recorded:
the fault this program exists to prevent, aimed at itself.

**Build:** a test with a table of `stage → (version, sha256 of the stage's source files)`. When a stage's
source changes, the test fails until someone either bumps the version or updates the hash with a comment saying
why no output can change. Include `llm.py` in the hash of the stages that import it.

### D7. Old software's results are reused without a word (S)

Package versions are in receipts but not in keys (right: otherwise every upgrade reruns everything). But after
upgrading faster-whisper, nothing tells a person that half the corpus was transcribed by the old version.

**Build:** `plan` and the grid mark a cached cell whose receipt's packages or tool versions differ from what is
installed now ("reused; made with faster-whisper 1.2.0, now 1.3.1"). `ontherecord plan --refresh STAGE` forces
those to run again.

### D8. Smaller items

- **`transcribe.model` choices** (`transcribe.py:25`) allow four names, while the help says "or a local
  CTranslate2 directory". Remove the list (rule 4), so a lab can use a model tuned for its language.
- **English is assumed** in `download.py` (`subtitleslangs: en`), the default `language: "en"`, the date
  regexes and `library.stem`. Do not change defaults (rule 2). Give the Transcribe form and `presets.py` a
  language choice with "detect" first, and make the search stemmer a no-op for non-English projects.
- **Review sets store absolute paths** to audio in the store (`clip.path`). Move the workspace and every set
  loses its audio. Store run, item and artifact, and resolve when serving; keep reading the old form.
- **`run.json` is rewritten whole on every cell change** (`runner._cell`). Fine at 11 items by 8 stages. At
  2,000 clips it is millions of writes of a growing file. Save at most once a second and at each batch end.
- **The Library reads every run record and receipt on every request**, and search loads every transcript per
  query. Fine at 29 runs. When `/api/library` takes more than a second, add an index in SQLite that can be
  deleted and rebuilt from the run records. Measure first; do not build it early.
- **Plugin stages** come from an environment variable (`ONTHERECORD_STAGES`). Also accept Python entry points
  (group `ontherecord.stages`) and a `stages:` list in `machine.yaml`.
- **`recipes/eleven-*.yaml`** repeat the same eleven links four times. `url_file` already exists; use it.
- **The runner learns that an item finished by matching log text** (`runner.py`, `" ..."`, `" done in "`,
  `" FAILED"`). It works. If it is ever touched, have the worker print one marked line per event instead.
