# Architecture audit and roadmap (November 14, 2026)

An audit of On the Record at commit `12e3419`, asking one question: what stops a social scientist with a
different study (interviews, classrooms, focus groups, video, another language, their own codebook) from using
this, and what should change so they can. Written for whoever builds next, person or agent. Each item says what
is wrong, where, why it matters, what to build, and how to know it is done.

Baseline when this was written: 96 tests pass, 1 skipped. The workspace on shiro holds 29 runs, 217 receipts and
3 review sets.

**Revised later on Nov 14.** The first version froze every existing stage's output and defaults, to protect the
store. Jeff then said the project is pre-launch and anything may be broken and rerun if the result is better
(his words are in the next-but-one section). That changed the design, not only the rules: A1 to A3, B2, D3, D4,
D8 and the order of work were rewritten, and A4 is new. If you read the first version (commit `9989228`), read
those again.

## How to use this document

- Read "The diagnosis" and "What may break, and what may not" before touching anything. The second is the part
  an implementer is most likely to get wrong, in both directions: by protecting old files nobody needs, and by
  damaging the few things that cannot be made again.
- Items are numbered (A1, B3...) and ordered by dependency inside each part. "Order of work" at the end gives one
  sequence across all parts.
- Sizes: S is under half a day, M is one or two days, L is most of a week.
- Each item has a "Done when" line. Do not call an item done on anything less.
- Where an item says "decide with Jeff", stop and ask. Those are choices about his research, not about code.

## The diagnosis

**The engine generalized. The data did not.**

The engine is the recipe, the runner, the content-addressed store, receipts, checks, the `same_source` trace and
the one-at-a-time queue (`recipe.py`, `runner.py`, `worker.py`, `store.py`, `hashing.py`, `jobs.py`). None of it
knows what a council meeting is. It is small, tested and sound. Keep it as it is.

Everything above the engine was ported from two specific projects and still has their shape:

1. **Every stage invents its own file format, and every reader finds data by stage name.** `transcript.json`,
   `aligned.json`, `blocks.json`, `words.json` and `comments.json` are five different shapes for "stretches of a
   recording, with text, maybe a speaker, maybe a label". The Library, Compare, Reviews, the assistant's tools
   and the page's previews each name the stages they know and reach into those shapes:
   - `library.py:64-76` (`_view`) lists six stage names by hand and special-cases `nemotron_transcribe`.
   - `library.py:210-221` (`HEADLINE`) is a table keyed by stage name.
   - `reviews.py` `from_run` has four kinds, each tied to named stages and their JSON fields.
   - `static/app.js:510-513` previews an output by checking `name === "blocks"`, `name === "comments"`.
   - `tools.py:188` is a `public_comments` tool.
   - Count of stage-name string literals outside `stages/`: 32 in `library.py`, 11 in `reviews.py`, 21 lines in
     `app.js`.

   So adding one new kind of work means editing about eight files. The Nemotron stage shows the cost: to fit in,
   it had to imitate pyannote's and Whisper's exact files (two RTTMs and a stats file it has no real use for).

2. **Coding, the central act of qualitative research, is not a concept in the program.** There is no codebook.
   The machine codes through `extract_comments`, whose question, schema and prompt are fixed to public comment
   in Lancaster. People code on the Check page, where codes are ten key names stored inside one review set
   (`reviews.py:47`, placeholder names for a council meeting). The two write different shapes and never meet, so
   the program can answer "does the machine agree with my coders?" for exactly one hard-wired question.

3. **The unit of work is a recording, and everything smaller is buried.** Segments, turns, blocks and clips live
   inside JSON files with no shared ids. `stress_set` packs a whole dataset into one zip to pass as one item, so
   one bad clip of 218 reruns all 218 and no clip has its own receipt.

4. **The screens are arranged by mechanism, not by a researcher's day.** Build, Jobs, Results and Setup are
   engine words. The only path that needs no recipe is "Transcribe a recording". Coding by hand with your own
   codes needs a command line (`review new RUN --kind check --codes "..."`).

The fix for 1 to 3 is one idea: **a few shared data formats that stages declare, and readers that look for a
format, not a stage.** Parts A and B build that. Part C is the screens. Part D is smaller faults found on the
way.

## What may break, and what may not

**Jeff, Nov 14:** "We're still in a pre-launch state, and have local copies of all test data and the ability to
re-download, or re-run anything. So if there is a breaking change with the way things are done that would ruin
or force a re-run of the Lancaster meeting data or of various voice-stress data, but would improve the project
long-term, then just go ahead and make the breaking change." And: "don't worry about the time/effort/cost of
re-running ... if there's a better way I'd like the better way."

That covers On the Record's own code, file formats, store, run records and recipes. Do not ask again before
changing a stage's output, a default, a setting or a recipe.

### What may not break

**R1. People's answers.** They are the one thing here that cannot be rerun. Today:

| Set | Answers | Its audio comes from |
|---|---|---|
| `stress-clips-which-word-is-stressed-20261023` | 172 | `~/src/AITranscribe/stress_search` (outside the store) |
| `check-water-mains-and-press-conference-20261024` | 6 | `<workspace>/store/audio/...` (64 items) |
| `gold-sample-public-comment-20261023` | 0 | `~/src/hands_on_dl/downloads` (141 items; 39 have none) |

The gold set has no answers yet, but its `set.json` is the pre-registered sample: never regenerate it. Before
any change to `reviews.py` or to the store, copy `<workspace>/reviews/` somewhere safe. Any change to how
answers are read needs a test that the old `answers.jsonl` files still load and score the same (the stress set:
WhiStress 47 of 49). Never remove a store entry that a review set's audio points to.

**R2. The papers' code.** It lives in `~/src/hands_on_dl` and `~/src/AITranscribe` and stays frozen. On the
Record reads from those folders and never writes to them. The ISLS paper's numbers come from there, so nothing
done here can change them.

**R3. The inputs rule.** Nothing a stage reads may come from outside its settings and inputs: not a project
file, not item metadata, not speaker names, not the clock. If a stage needs it, it arrives as an input artifact
with a hash (C4 and D4 are the two places this bites). This is what makes a cache key complete; it is not about
cost.

**R4. What STATUS.md decided.** One thing at a time, nothing goes online unless asked, every download pinned by
SHA-256, the server answers only this machine, reviews are blind by construction, the answers log is
append-only.

### How to break things well

**K1. Know what a change costs.** Read `hashing.py` and `recipe.py:resolve_settings`. A stage's version, every
setting (defaults filled in) and every input's hash go into the key. So changing an output's bytes, a default,
or the list of settings gives new keys for that stage and everything after it. That is now allowed. It must
only never happen by accident.

**K2. Bump the version, every time.** If a stage's output changes shape and its version does not, the cache
hands old-shape files to new readers and nothing says so. Build D6 (the test that enforces this) before
anything else.

**K3. No adapters, no shims, no "legacy" paths.** When a stage's output changes, change every reader in the
same commit and delete the old code. Do not write a reader that accepts both shapes, a converter for old store
entries, or a fallback for old run records (`Library._steps` has one today, "for records made before those
existed": delete it). An agent's instinct is to keep the old thing working beside the new. Here that instinct
is wrong: two shapes is the fault this audit found.

**K4. One break, one rerun.** Do all the format work on one branch (`formats`), then rerun the corpus once at
the end, through the queue. Not once per item.

**K5. The rerun must reproduce the recorded numbers.** This is the acceptance test for the whole branch. From
`docs/researchathon-notes.md`:

- `eleven-left`: 189 speakers and 154,212 words. Neither the audio, the models nor their settings change, only
  the files they are written to, so these must match exactly.
- `eleven-average`: 1 speaker, 0 words.
- `eleven-as-coded`: `same_source` fails on all 11.
- WhiStress: 218 of 218 on StressTest and 202 of 202 on StressPresso, item for item against the poster.
- 1,325 speech blocks from the left-channel run: `turns` with `max_gap_s: 30, max_turn_s: null` must give the
  same count (A3).
- 121 public comments: expect a number close to this and not equal, because the generic `code` stage builds
  its own schema (B2). Record the new number in the notes with the reason.

If a number that must match does not, stop and find out why before touching the notes.

**Nov 16, the rerun: everything matches except one meeting's words, and the reason contradicts the premise
above.** RTTMs byte-identical everywhere (189; 1 per meeting; `same_source` fails on all 11), WhiStress marks
byte-identical (218, 202), 0 words averaged, 121 comments. But `X3DupuiqLts` gave 154,205 words in all, not
154,212, so 1,323 turns, not 1,325: Whisper float16 is not deterministic on this card at one near-tie in that
meeting. The same audio, settings, packages and call gave a third result on a direct repeat. Details in STATUS.md.
Waiting on Jeff before K6, the notes and the merge.

**K6. Old runs are deleted, not read.** Once K5 passes, the 29 old runs and their store entries go. Add
`ontherecord store prune` (S): it lists, and with `--delete` removes, store entries that no run record in
`runs/` and no review set (R1) refers to. Delete the old run folders first, then prune.

**K7. Tidying is allowed where an item takes you.** `server.py` is one 770-line function and `app.js` one
1,375-line file. When A2 has you rewriting a part, split it: `server.py` into one router per area, `app.js`
into native ES modules (`<script type="module">`), one per tab. Still no framework and no build step. That
limit comes from the installers and from "nothing is fetched", not from compatibility.

## Part A. Shared data formats (the spine)

### A1. Artifact types, written by the stages themselves (L, with A2) — the spine

**Done Nov 14, on `formats`: `fc595c6` (engine) and `51d2637` (stages).** Decided while building: when the step
that makes an input's type makes two of it (diarize's `speakers` and `speakers_exclusive`), the one named like the
input wins, else the first declared; `from:` also takes `step.artifact`. `table` and `other` are opaque and wired by
name. The `same_source` trace stays keyed by the producer's artifact name, so transcript → aligned → turns is one
line, not a mix. `align` lost `overlap_mode`: wire `from: {speakers: diarize.speakers_exclusive}` instead.
Receipts are `receipt_version: 2`, with each output's type.

**What.** Three formats cover nearly everything:

- **segments**: stretches of one recording.
  `{"format": "segments/1", "unit": "segment" | "turn" | "clip" | "interval",
    "units": [{"id": "t0007", "start": 12.3, "end": 19.8, "text": "...", "speaker": "SPEAKER_02",
               "from": ["s0031", "s0032"],
               "words": [{"start", "end", "word", "p", "alts": [...]}]}]}`
  `text`, `speaker`, `from` and `words` are optional. A unit with no text is legal: that is what a stretch of
  video is (Part E). `from` names the units of the input this unit was built from, so a code on a turn can be
  followed down to Whisper's segments.
- **annotations**: labels on units or on spans of time.
  `{"format": "annotations/1", "codebook": {"name", "sha256"}, "by": {"kind": "model" | "person", "id": "..."},
    "annotations": [{"id", "target": {"units": ["t0007", "t0008"]} | {"start": 12.3, "end": 19.8}
                                    | {"unit": "t0007", "word_from": 3, "word_to": 9},
                     "code": "public_comment", "attributes": {"position": "oppose", "summary": "..."},
                     "note": ""}]}`
  Three target kinds on purpose: whole units (what a model returns), a time span (video, overlapping speech),
  and a word span inside a unit (what the Check page records).
- **speakers**: who spoke when. RTTM, as now.

`Stage.needs` and `Stage.makes` become maps from a name to a type:
`makes = {"transcript": "segments"}`, `needs = {"audio": "audio"}`. Types: `media`, `audio`, `info`, `segments`,
`speakers`, `annotations`, `table` (CSV), `other`.

**Wiring by type.** In `parse_stages`, a needed input is filled by the latest earlier step that makes an
artifact of that **type** (today: of that name). `from:` still overrides, naming a step. The `same_source`
trace is unchanged. This is what lets a stage say "any segments" and work after Whisper, after Nemotron or
after an imported transcript.

**Every stage is rewritten to write these directly, with its version bumped (K2):**

| Stage | After |
|---|---|
| `transcribe` | `transcript`: segments, unit `segment` |
| `diarize` | `speakers` (overlap kept), `speakers_exclusive`, `diarization_stats` |
| `align` | needs segments and speakers; makes `aligned`: segments with `speaker` |
| `nemotron_transcribe` | `transcript`: segments **with speakers already**, plus `nemotron_raw`. It stops writing two RTTMs and a stats file in imitation of pyannote, and `align` is no longer needed after it. |
| `word_choices` | `words`: segments with `words` and their `alts` |
| `blocks` | deleted; `turns` replaces it (A3) |
| `extract_comments` | deleted; `code` with a codebook replaces it (B2) |
| `stress_set`, `whistress`, `stress_read` | see A4 |

**Check what is written.** `artifacts.py` holds `validate(path, type)`. The worker calls it on every typed
output before it writes the receipt, and a stage that writes a malformed file fails there, with the field
named. A format's rules live in one place and no reader needs to be defensive.

**Trap.** K3. No reader for the old shapes. `artifacts.py` is a validator and two loaders, not an adapter.

**Done when:** every built-in stage declares typed `needs` and `makes`; `validate` rejects a fixture with a
missing id, a duplicate id and an end before its start; a recipe with `nemotron_transcribe` then `turns` (no
`align`) parses, and so does `transcribe`, `diarize`, `align`, `turns`.

### A2. Readers look for a type, not a stage (M) — lands with A1, on the same branch

**Done Nov 14, `51d2637`** (`test_any_stage_making_segments_and_annotations_shows_in_the_library`,
`test_no_reader_names_a_stage`). The review kind `comments` is now `codes`; the tool is `coded`. One departure:
the Library's transcript is the segments with text, preferring speakers, **then segment-sized units over turns**,
then the latest (the audit said "latest"; turns of a whole public comment read badly as transcript lines). Compare's
WhiStress headline is now top-1 (a flat metric), not F1. Still to do: rerun the assistant eval after the rerun (it
reads the real workspace, whose Library is empty on this branch until then).

A1 changes what every stage writes, so the Library, Compare, Reviews, the assistant's tools and the page break
the moment it lands. A1 and A2 are one piece of work.

**What.** One helper: "for this run and item, the latest step that makes an artifact of type T", from the run
record's stages and their declared types. Write each step's `makes` types into `run.json` when the run starts,
so a run whose plugin stage is not installed here can still be read.

- `Library._view`: the transcript is the latest `segments` artifact that has text, preferring one with
  speakers; the audio is the `audio` that step's inputs trace to (keep this: the player must play what the
  transcriber heard); the codes are every `annotations` artifact, listed by step name.
- `HEADLINE` moves to the stages: `headline = ("words", "words")` on `Stage` (a metric and its wording), read
  by `compare`.
- `app.js`: preview by type. One table for any `segments`, one for any `annotations` (columns from the
  attributes present), raw JSON for `other`.
- `reviews.from_run`: `transcript` and `speakers` kinds take any `segments`; `check` takes any `segments` with
  `words`; the `comments` kind becomes "any `annotations`" (sample units half from those coded and half from
  the rest, ask the codebook's question).
- `tools.py`: `public_comments` becomes `coded` ("what was coded as X, across recordings"). A tool description
  changes, so rerun the assistant eval.

**Why.** After this, a new transcriber, unit builder or coder shows up in the Library, Compare and Review with
no edits outside its own file. That is the test of whether the architecture generalized.

**Done when:** `tests/stages_for_tests.py` has a toy stage making `segments` and one making `annotations`, and a
run of them shows a transcript and a codes tab in `Library.recording()` with no production code naming them.
Outside `stages/`, `presets.py` and `bootstrap.py`, no file contains a stage name as a string (a test greps for
this).

### A3. A `turns` stage, replacing `blocks` (S)

**Built Nov 14, `51d2637`.** On the old left-channel and as-coded `aligned.json` files, `turns.merge` gives 1,325
and 2,773, meeting by meeting. Done when the rerun gives 1,325 (K5).

**What.** Needs any `segments` with speakers; makes `turns` (segments, unit `turn`, each with `from`).
Settings: `max_gap_s` (default 5) and `max_turn_s` (default 60, or `null` for no limit; a longer turn is cut at
a segment boundary and its parts numbered). It merges consecutive segments of one speaker.

It replaces three copies of the same logic, all deleted in the same commit: `blocks.merge_segments`,
`reviews.turns` and the Check set builder (which then reads a `turns` artifact). `blocks`' council heuristic
(`recurring` against `commenter_candidate`, `blocks.py:44-51`) goes with it. It only ordered a coder's
attention, and it means nothing in an interview.

The council recipes set `max_gap_s: 30, max_turn_s: null`, which is what `blocks` did.

**Done when:** on the left-channel run, `turns` with those two settings gives 1,325 units (K5).

### A4. Datasets as recordings, not as one zip (L) — after B4

**What is wrong.** `stress_set` packs StressTest's 218 clips and their labels into one `set.zip` and passes it
through the run as a single item, because an item was the only unit the runner had. So no clip has a receipt,
one bad clip reruns all 218, the Library cannot show them, and `whistress` and `stress_read` each carry their
own scoring code.

**Build.**

1. `ontherecord dataset get slprl/StressTest`: a queued download at the pinned revision, writing the clips and
   a `manifest.csv` (id, path, and the label columns) into the archive. It replaces the `stress_set` stage.
2. A recipe takes the manifest as its source (D4). Each clip is an item.
3. The labels reach stages through D4's `metadata` stage, as `annotations` by a person. WhiStress's marks are
   `annotations` by a model, with word-span targets.
4. Scores across clips are **reports, not stages**: a report reads a finished run's outputs and computes a
   number over all its items. B4's `agree` is the first report (WhiStress's marks against the labels). Add a
   second for `stress_read`'s accuracy with its interval. A stage works on one item; anything across items is
   a report. Reports are shown on the run's page and are cheap to recompute, so they are not cached.
5. This needs D8's fix to `run.json` first (420 items, each cell change rewriting the whole file).

**Why it is worth an L.** It is the second field of study running on the same formats, coders and agreement
screen as the first, which is the claim the whole audit is about.

**Done when:** K5's WhiStress numbers are reproduced item for item; deleting one clip's store entry and
submitting again runs one clip.

## Part B. Coding as a first-class thing

### B1. Codebooks (S)

**Done Nov 14, `51d2637`** (`codebooks.py`, `codebooks/public-comment.yaml`, US spelling in its field help).

**What.** A codebook is a YAML file, hashed like a prompt (`Setting(kind="file")`), so its full text lands in
every receipt:

```yaml
name: public-comment
question: Is this speech by a member of the public addressing the body?
multiple: false            # may one unit carry several codes?
codes:
  - id: public_comment
    name: Public comment
    definition: A resident or stakeholder addressing the body with an opinion, concern, request or question.
    include: ["speaking at a public hearing", "reading a statement for a neighbor"]
    exclude: ["council members", "invited presenters", "the clerk calling names"]
attributes:                # optional free fields the coder also fills in
  - {id: position, choices: [support, oppose, mixed, neutral_or_question, unclear]}
  - {id: summary, help: one or two sentences in plain words}
```

Put shipped examples in `src/ontherecord/codebooks/` (found the way `resolve_file` finds prompts) and a
project's own in its project folder (C5). Validate on load: unique ids, non-empty definitions.

**Why.** The codebook is the one object a human coder, a model coder and the write-up all share. Today its
content is spread over a prompt file, a Python schema and a list of key names.

### B2. The `code` stage (L) — the highest-value item here

**Built Nov 14, `51d2637`.** Toy codebook against a fake server, cached on a second plan, `extract_comments` gone:
done. Left: the council recipe on one real meeting through the queue, its codes in the Library. The model's
context setting is `context_tokens`, since `context` is the research setting. It reads no title (R3), so the
user message has none.

**What.** A new stage that applies any codebook to any `segments` artifact and writes `annotations`.

- `needs = {"units": "segments"}`: any segments, by A1's wiring. In a recipe: `- code: {codebook: my.yaml}`
  after `turns`, or with `from: {units: STEP}` to code another step's units.
- Settings: `codebook` (file), `lens` (file, optional: a theoretical stance put before the codebook),
  `context` (`unit`: each unit alone; `window`: each unit with `window_size` neighbors either side as grey
  context; `whole`: the whole recording at once, answering by unit id), `mode` (`classify`: every unit gets an
  answer; `find`: list the stretches that match, as `extract_comments` does), and the model settings
  `open_model` already takes (`endpoint`, `model`, `context_tokens`, `offload`, `thinking`, `temperature`,
  `seed`, `max_tokens`).
- The model answers **by unit id only**, never by quoting. Keep this from `extract_comments`: the coded text is
  then the transcript's own bytes and can be checked. Build the JSON schema from the codebook (code ids as an
  enum; attributes as declared).
- Checks: `parsed` (fail), `unknown_ids` (warn), `unknown_codes` (fail), `coverage` in classify mode (warn when
  units got no answer), `windows` (how many pieces; warn when a `whole` recording did not fit and was cut).
- Outputs: `annotations` (the new format, with the raw responses kept beside the parsed ones, as now) and
  `annotations_csv`.
- Reuse `llm.py` and `usage.llm_metrics`. Move the windowing and merging functions out of
  `extract_comments.py` into the new stage before that file is deleted.

**Why `context` and `lens` are settings.** They are Jeff's two research claims made runnable. The ISLS paper is
about what batching changes: `context: unit` against `whole` is that experiment in one line. His "LLM coders can
forget" idea (the same coder under several theoretical lenses, like rotating graduate coders) is `lens`. With
receipts, two runs that differ in only one of these are provably that and nothing else.

**It replaces `extract_comments`, which is deleted (K3).** Ship `codebooks/public-comment.yaml`, carrying the
same definition, exclusions and the six fields as attributes. Add one more setting, `instructions` (a file,
optional): when given, it is used as the system prompt in place of the text generated from the codebook. The
council recipes pass the paper's prompt there, word for word (`prompts/extract_public_comments_v1.txt`), with
`mode: find`, `context: whole` and `turns` cut as in A3.

**Expect a different count.** The schema the model is held to is now built from the codebook, so its field
descriptions differ from the paper's hand-written schema, and the left-channel run's 121 comments will move a
little. That is expected (K5): record the new number. The paper's own count is reproduced by the paper's own
code, in hands_on_dl (R2).

**Done when:** a recipe with `turns` then `code` under a toy codebook passes against the test stub server; the
council recipe runs on one real meeting through the queue and its codes show in the Library (A2);
`ontherecord plan` shows it cached on a second submit; `extract_comments.py` and its tests are gone.

**Done Nov 15, `51d2637`, checked on `20261115-220828-jan29-left-comments`:** 3 public comments (the old stage
found 4), shown by `Library.recording`, and the whole recipe plans cached again. Left to fix after the rerun: the
annotations' `by.id` is the model's full local path (it names the home folder); it should be the file name.

### B3. People and models write the same annotations (M)

**What.**

1. **Fix annotator identity first (a real fault, see D1).** Today every answer is recorded `by: "me"` and the
   latest answer per item wins regardless of who gave it.
2. A review set made for coding carries the codebook (its name and sha256, and the codes themselves so the set
   stays self-contained and unchangeable). `review new RUN --kind code --codebook my.yaml` replaces `--codes`.
   Keys 1-5 and Q-T go to the first ten codes; the rest are reached by a type-to-filter list. Show each code's
   definition on hover or on `?`: a coder who cannot see the definition is not applying the codebook.
3. `ontherecord review export SET --annotations` writes one `annotations` file per annotator, in the A1 format.

### B4. Agreement between any two coders (M)

**What.** `ontherecord agree A B [C...]`, where each argument is an annotations source: a run's step
(`RUN:step`) or a review set's annotator (`SET:name`). Output per code: how many each side applied, agreement,
Cohen's kappa for two coders, Krippendorff's alpha for more or for missing data, and with one side named as the
reference, precision, recall and F1. Plus the units they disagree on, as a list that opens in the player.

Unitizing: a model codes whole units, a person on the Check page codes word spans. Compare at the unit level (a
unit carries a code if any span in it does) and say so in the output. Do not invent a span-level statistic.

**Why.** This single command answers the questions a methods section needs: person against person (is the
codebook usable?), person against model (can the model be trusted?), model against model across lenses, context
sizes or model files (what does the setting change?). It is also the natural result screen for B2.

**Trap.** Look the formulas up (Krippendorff 2011, "Computing Krippendorff's Alpha-Reliability") and test
against a worked example from the source. Do not write alpha from memory.

**Done when:** tests reproduce a published worked example for kappa and for alpha; `agree` on the gold sample
set against `extract_comments` reproduces the agreement `review score` already reports for it.

### B5. Variants in a recipe (S, after B2)

**What.** Sugar over `as:`.

```yaml
- code: {codebook: frames.yaml}
  variants: {lens: [none, conflict.txt, care.txt], context: [unit, whole]}
```

expands at parse time into six ordinary steps named `code-lens-conflict-context-unit` and so on. Nothing in the
runner changes. `stress-benchmarks.yaml` shows the need: five hand-written `stress_read` entries.

## Part C. Usable without a command line

### C1. Arrange the screens by the work (M)

**What.** Order and name the tabs as a study goes: **Recordings** (the Library, with Import and Transcribe
inside it) → **Check** (transcripts by ear) → **Code** (by hand, or by model) → **Compare** (agreement, and
two runs side by side) → **Export**. Put Build, Jobs and Results under one **Runs** tab for people who want the
engine, and Setup under a gear. Ask stays.

Every action starts from a recording or a selection of them: tick recordings in the list, then "Transcribe",
"Check by ear", "Code by hand", "Code with a model", "Export". Each button writes a recipe or a review set
behind the scenes and shows it ("what will run", with the time estimate that already exists).

**Why.** A researcher thinks "these twelve interviews", not "a recipe whose source lists twelve files". The
recipe stays the record; it stops being the entry point.

**Trap.** Reorder and relabel; do not rebuild. The existing panels move, they are not rewritten.

### C2. A codebook editor (M, with B1)

A form: add a code, name it, define it, give examples to include and exclude; add attributes. It writes the
YAML of B1 into the project folder. Without this, B2 is a feature for programmers only. Offer "start from a
copy" of a shipped codebook.

### C3. Plain errors (S)

`worker.py:113-116` stores a Python traceback as the cell's error and the page shows it. Add
`class UserError(Exception)` in `stages/base.py` with a message and a `fix`. Raise it for the failures a person
can act on: no Hugging Face token, the model's terms not accepted, model file not downloaded, ffmpeg missing,
out of GPU memory, a file with no audio stream. The cell shows the message and the fix; the traceback goes to
the log only. Unknown exceptions keep today's behavior with a first line that says "this is a fault in the
program; the log has the details".

### C6. Getting work in and out (M for the first three, L for the rest)

Researchers do their analysis in NVivo, ATLAS.ti, MAXQDA, ELAN, Praat, R or Excel. If work cannot move both
ways, the program is a detour.

**Out.** Today `.txt`, `.srt` and `.vtt` are built in the browser (`app.js:639`), so the command line, agents
and the `Transcripts/` folder cannot make them. Move them to a new `exports.py`, and add:

1. `.txt`, `.srt`, `.vtt` (moved), with speaker names applied. (S)
2. `.csv`, one row per unit: recording, its metadata columns (D4), unit id, start, end, speaker, text, and one
   column per code and attribute, per coder. This is what R and Excel users need and it is cheap. (S)
3. `.docx`, one paragraph per turn with the speaker and a time stamp. All three QDA programs import this. (S)
4. ELAN `.eaf` (a tier per speaker, a tier per codebook) and Praat `.TextGrid`. (M)
5. REFI-QDA `.qdpx` (codebook and coded segments, exchanged by NVivo, ATLAS.ti and MAXQDA). (L) Read the
   standard at qdasoftware.org before writing a line; do not write the XML from memory.

Every export ends with, or sits beside, its provenance: run id, the receipt keys of the transcript and the
annotations, the codebook's sha256. That line is the product.

**In.** A stage `import_transcript` making `segments` from an existing transcript: `.vtt` and `.srt` (Zoom and
Teams write these, with "Name: text" lines that give speakers), and plain text with "Speaker: text" paragraphs.
Many labs already have transcripts and only want checking, coding and agreement. With this they can start at
Check or Code with no Whisper and no GPU. (M)

### C8. Windows and macOS (L) — the largest adoption risk

Most social scientists use a Mac or a Windows laptop with no NVIDIA card. Neither system has been tried
(STATUS.md, week 4). Do the Windows walkthrough first, since Jeff has the machine.

On a Mac, Whisper runs on the processor (`bootstrap.fit`: `large-v3-turbo`, `int8`), because CTranslate2 has no
Apple GPU backend. **Measure before building anything:** minutes of compute per hour of audio on a real Mac. If
it is worse than about 30, add a second transcriber as a new stage (whisper.cpp has Metal support) that makes
the same `segments` type. After A1 and A2 that is one file. Check current backend support in the projects'
own documentation at the time; do not rely on this note.

## Part D. Faults and risks found on the way

### D1. Two annotators overwrite each other (S) — fix before anyone else codes

**Done Nov 14, `a7a9fa1`.** Both answers survive in export and scoring (`test_two_annotators_never_overwrite_each_other`).
Found while building: the Review tab already had an "answering as" box (the Check page did not), so the fault was the
keying, not the sending. `score` pools every annotator's pairs and adds `by_annotator`; `review score --by NAME`.

`reviews.latest` (`reviews.py:140`) and `scoring_answers` (`reviews.py:286`) key answers by item only.
The server accepts a `by` field (`server.py:89`) but neither page ever sends one, so every answer is `"me"`.
If a second person opens the same set, their answer replaces the first person's in progress, scores and export,
and the set looks finished to them from the start.

**Build:** an annotator name, asked once per browser and shown in the header; sent with every answer and
reveal. Key `latest`, `scoring_answers`, `progress` and `export_rows` by `(item, by)`. `machine_seen` is per
annotator. Progress is per annotator. Old rows with `by: "me"` stay valid as an annotator called "me".

**Done when:** a test has two annotators answer the same item differently and both answers survive in export
and in scoring.

### D2. Local files are hashed in full on every plan (S)

`recipe.source_identity` runs `sha256_file` on every local source, once per `Runner`, and a `Runner` is built
for every plan, estimate and submit. Fifty two-gigabyte interview videos is 100 GB read before anything starts,
each time the Build tab refreshes. This will be the first thing an interview researcher feels.

**Build:** a cache in the workspace (`hashcache.db`, SQLite): resolved path, size, mtime in nanoseconds →
sha256. Use it in `source_identity`. A changed size or mtime rehashes. `ontherecord plan --rehash` ignores the
cache. Say in AGENTS.md that a file altered with its size and mtime preserved will not be noticed.

### D3. A setting can say one thing and the key another (M) — on the `formats` branch

**Done Nov 14, `51d2637`** (`test_auto_is_settled_before_the_key_so_machines_get_different_keys`,
`test_a_compute_type_the_card_lacks_fails_at_plan_time_with_the_fix`). Compute types follow CTranslate2 4.8.3's
source (looked up: float16 needs compute capability 7.0, int8 needs 6.1 or 7.0+).

`transcribe.py:55-64`: on a card without fast float16, `compute_type: float16` silently becomes `int8_float16`.
It is logged and put in the metrics, but the key still says float16. `device` is `in_key=False` everywhere,
though a transcript made on the processor is not byte-identical to one made on a GPU. The day a store is shared
between machines (the plan for Slurm on ROAR), the laptop reuses the cluster's result under the laptop's
settings, or the reverse.

**Build.** Settle `auto` before the key is computed.

- Add `Stage.resolve(settings, machine) -> settings`, a classmethod the runner calls when planning. It turns
  `device: auto` into `cuda`, `mps` or `cpu` and checks `compute_type` against the card, using `hwdetect.py`
  (standard library, already what `bootstrap.fit` uses). The resolved values are what gets hashed and recorded.
- `device` becomes `in_key=True` in every stage.
- No silent fallback at run time. If the card cannot do the compute type asked for, the stage raises a
  `UserError` (C3) naming the ones it can. `presets.py` already picks the right one per machine.
- `offload` (how much of a model sits in RAM) stays out of the key and in the receipt, as now.

**Done when:** a test plans one recipe for a fake CUDA machine and a fake CPU machine and gets different keys
for `transcribe`; a recipe asking for float16 on a fake card without it fails at plan time with the fix in the
message.

### D4. Recordings have no metadata (M)

`Item` is `id, url, path, title`. A study's recordings have a participant, a site, a condition, a date, a wave.
Today the date is guessed by matching an English month name in the title (`library.py:196`,
`extract_comments.py:60`), and nothing else exists. Exports without these columns need hand-merging in Excel.

**Build:** a recipe source `manifest: recordings.csv`, with columns `id`, `path` or `url`, optional `title` and
`date`, and any others. The others become the item's metadata, shown in the Library and written to exports.

**R3 applies.** Metadata is not part of any key (relabelling a participant must not rerun Whisper), so no
stage may read it. It lives in the run record. A stage that truly needs a per-recording value (true labels for
scoring) gets it as an input artifact from a small `metadata` stage that hashes that recording's row.

This also gives item ids a proper answer. Today a local file's id is its file name (`recipe.item_for_file`), so
`P01/audio.m4a` and `P02/audio.m4a` collide (the recipe is refused, correctly, but the only remedy is to name
each file by hand) and renaming a file makes it a new recording that is processed again. With a manifest the id
is the researcher's own. Without one, when names collide, prefix parent folder names until they are unique.

**Considered and rejected on their merits:** ids from content hashes (nobody can read them in a folder, a grid
or an export), and dropping the item id from the key so that a renamed file reuses its results (two recordings
with the same bytes would then share one receipt that names only one of them).

### D5. Sending recordings off the machine is silent (S)

**Done Nov 14, `422c647`.** Refused at plan time (the runner), not in `open_model`, so nothing starts first.

Any stage with an `endpoint` setting accepts any URL (`extract_comments`, `stress_read`, and B2's `code`). A
recipe copied from a colleague can send a transcript to a remote server with nothing on screen but a URL in a
settings list. For data under an ethics protocol, that is the worst thing this program can do.

**Build:** in `llm.open_model`, when the endpoint's host is not this machine, refuse unless `machine.yaml` has
`allow_remote_endpoints: [host, ...]` naming it. When allowed, add a `leaves_machine` check with status `warn`
naming the host, so the plan, the grid and the receipt all show it. Off by default.

### D6. Nothing enforces "bump the version when the code changes" (S)

**Done Nov 14, `6431b9b`** (`tests/test_stage_versions.py`). The source set is the stage's module plus every package
module it imports, transitively, minus a short list that cannot change outputs (`base.py`, `envinfo`, `hashing`,
`bootstrap`, `config`, `usage`).

`Stage.version` is raised by hand. Forget once, and old outputs are reused for new code with nothing recorded:
the fault this program exists to prevent, aimed at itself.

**Build:** a test with a table of `stage → (version, sha256 of the stage's source files)`. When a stage's
source changes, the test fails until someone either bumps the version or updates the hash with a comment saying
why no output can change. Include `llm.py` in the hash of the stages that import it.

### D7. Old software's results are reused without a word (S)

Package versions are in receipts but not in keys (right: otherwise every upgrade reruns everything). But after
upgrading faster-whisper, nothing tells a person that half the corpus was transcribed by the old version.

**Build:** `plan` and the grid mark a cached cell whose receipt's packages or tool versions differ from what is
installed now ("reused; made with faster-whisper 1.2.0, now 1.3.1"). `ontherecord plan --refresh STAGE` forces
those to run again.

## What is good, on its merits

Not frozen, but there is no better design on offer for these, so change them only with a reason: the cache key
and its completeness rule (R3); receipts with defaults filled in (they become `receipt_version: 2` on the
`formats` branch); checks that stop an item; the `same_source` trace; building a store entry beside its final
place and renaming it in; the queue, one job at a time, detached from the page; pinned downloads; the
loopback-only server with its Host and Origin checks; blind reviews with an append-only log and a seeded order;
stage declarations that draw their own forms; time estimates from the machine's own receipts.
